# Designing an ASIC from scratch
Designing an ASIC from scratch isn't a common task; it may seem like an \"engineer's thing\", but it's actually much more accessible than it seems.
To design my first ASIC I started with the idea, for then move to learn an HDL (I've used Verilog) and then start designing the project.

![ASILUC 2D Image](/projects/ASILUCPreview.png)

## The idea
I started designing ASICs with a really easy project: develop one to works as an ALU!

I'm joking, it wasn't easy, but it wouldn't be funny if i started from an ASIC that made a led blink or something similar.

My first ASIC project is ASILUC: a simple ALU that may fit in a calculator.
ASILUC performs operations from two 8 bit numbers given in input, and returns a 16 bit number in output.
It supports some elementar commands like `SUM`, `SUB`, `MUL` and `DIV`.

My idea was to start from just a few simple functions, but prepare the field to eventually add other functions if the project grows.

## Where I started
I already had some basics of electronics, in particular about digital signals and logic gates.

Then I started by learning Verilog HDL, that to me looked quite easy and intuitive.

To learn Verilog, I've learned by doing the exercises on [https://hdlbits.01xz.net/wiki/Problem_sets#Verilog_Language](https://hdlbits.01xz.net/wiki/Problem_sets#Verilog_Language).
I found them not easy, but really funny and educative.

Once I felt secure about my Verilog, so when I understood how it works and I made an idea about where to start, I created the GitHub repo, based on [TinyTapeout/ttgf-verilog-template](https://github.com/TinyTapeout/ttgf-verilog-template) as template.

After preparing the repo, I setted up the environment by installing [yosyshq/oss-cad-suite-build](https://github.com/yosyshq/oss-cad-suite-build) to get the compilation and the simulation tools.

## Architecture and Design
I decided to project the ASILUC to have a simple and clear main file and some little modules made to be used inside the main or in other modules.

The main file in the *TinyTapeout* template has the following inputs and outputs:
```verilog
input  wire [7:0] ui_in,    // Dedicated inputs
output wire [7:0] uo_out,   // Dedicated outputs
input  wire [7:0] uio_in,   // IOs: Input path
output wire [7:0] uio_out,  // IOs: Output path
output wire [7:0] uio_oe,   // IOs: Enable path (active high: 0=input, 1=output)
input  wire       ena,      // always 1 when the design is powered, so you can ignore it
input  wire       clk,      // clock
input  wire       rst_n     // reset_n - low to reset
```

I decided to use those pins as following:
- `ui_in`: 8 bit input for the 2 numbers
- `uo_out`: 8 bit output for the result of the operation (or the error code)
- `uio_in`: uses only the lowest 4 bits for the operation code
- `uio_out`: uses only the highest 4 bits for the ASILUC status
- `uio_oe`: 8 bit pins that decide which pins of the `uio_in` and the `uio_out` are inputs or outputs, fixed at `8'b11110000`
- `ena`: ASIC enable, is always 1 when the design is powered
- `clk`: The clock, ASILUC is sincronous
- `rst_n`: Reset, active low

ASILUC is sincronous because the operations that executes need to be precise and is sensible to an eventual difference of time needed to effectuate different operations.

The ASILUC is devided in 3 modules:
- The main module
- The calculation module
- The clock counter module

The main module takes and validates the inputs, handles the clock timing and the outputs.
The calculation module do the selected operation on the given numbers and return the result of the operation.
The clock module simply counts when 3 clock cycles passes.

The coice of the 3 clocks is to allow the master to stabilize the signals (in input) and to read the outputs without the need to be perfectly sincronized to the ASILUC's clock.

## ASILUC states
ASILUC has 9 states:
- *Idle* - ASILUC does `NOP` unthil it reads a command on `uio_in`
- *Command Reading* - ASILUC is reading the command on `uio_in`
- *Command Accepted* - ASILUC accepted the command and is going to read the first number in input
- *Input (first number)* - ASILUC is reading the first 8 bit number on `ui_in`
- *Input (second number)* - ASILUC is reading the second 8 bit number on `ui_in`
- *Calculating* - ASILUC is performing the operation
- *Output (lowest byte)* - ASILUC is printing on `uo_out` the lowest 8 bit of the result
- *Output (highest byte)* - ASILUC is printing on `uo_out` the highest 8 bit of the result
- *Error* - An error occuried, on `uo_out` is printed the error code

### ASILUC status codes table
|Sequence|Operation|Duration (clk)|busy|status|highByte|error|
|---|---|---|---|---|---|---|
|Ø|Idle|∞|0|0|0|0|
|0|Command Reading|0-2|0|0|0|0|
|1|Command Accepted / Input (first number)|3-5|0|1|0|0|
|2|Input (second number)|6-8|0|1|1|0|
|3|Calculating|Variable|1|0|0|0|
|4|Output (lowest byte)|0-2 (After Calculating)|1|1|0|0|
|5|Output (highest byte)|3-5 (After Calculating)|1|1|1|0|
|Ø|Error|0-2|0|0|0|1|

This is the table that describes the order of the ASILUC's states (Idle and Error are out of the order because Idle is the default status and Error is a special status).

Every state has a fixed duration:
Idle persists unthil a command is given in input;
Command Reading is 3 clock long;
Command Accepted / Input (first number) are 3 clock long, and they happens together;
Input (second number) is 3 clock long;
Calculating is variable;
Output (lowest byte) is 3 clock long;
Output (highest byte) is 3 clock long;
Error is 3 clock long.

## How it works
ASILUC's default behavior is `NOP`.
In this status, all inputs (`ui_in`) are ignored.

When `uio_in` strictly changes from `NOP` to one of the operations, ASILUC starts the command reading: it waits **three clock cycles** to read the command associated with the operation to be executed, so the signal has time to stabilize, preventing errors.
Once ASILUC reads the command, it reads the first 8-bit number from `ui_in` for **3 cycles** (the value saved is the one on the third cycle), and then, it reads the second 8-bit number for **3 cycles**.

`uio_in` ignores any unexpected command changes: the command read on the third cycle after the change from `NOP` is the one executed.
If the command returns to `NOP` before the third cycle, the reading is aborted.

Meanwhile, `uio_out` uses the 4 bits to signal the status of ASILUC:
- `uio_out[7]`: *busy* - 1 if ASILUC is executing operations or if ASILUC put a result byte on `uo_out`.
- `uio_out[6]`: *status* - 1 if ASILUC put a result byte on `uo_out`, if ASILUC is reading a number on `ui_in`, or if the given command has been accepted.
- `uio_out[5]`: *highByte* - indicates whether the byte on `uo_out` is the high byte (2nd byte of out) or the low byte (1st byte of out), or indicates whether the read number on `ui_in` is the second or the first.
- `uio_out[4]`: *error* - 1 if an error occurred.

ASILUC processes the operation in the time it needs, maintaining *busy* at 1.
Once ASILUC finishes processing the operation, it sets *status* to 1 and puts the low byte of the result on `uo_out` (which, until this point, has always been `0x00`) (*highByte* at 0) (keeps the low byte stable for **3 cycles**), and then the high byte of the result (*highByte* at 1) (keeps it stable for **3 cycles**).

Afterwards, it returns with *busy* at 0, *status* at 0, *highByte* at 0, *error* at 0, and `uo_out` at `0x00`.

The process restarts, listening to `uio_in` again.

## How I tested it
To test ASILUC I first tested the submodules calculation and clock counter.
Thanks to the *OSS CAD Suite* I was able to run some tests (that I wrote in a specific Verilog file) to see the behaviour of the modules and visualiza the waveforms.

For the phase timer it was really easy to test, just see if the last cycle bit is set when the clock is at the thirth iteration.

The calculation module was a little more complex to test, it effectuate some operations on the given numbers and check the result.

Testing the entire ASILUC was easyer because the TinyTapeout template provides a testing template in python to edit, so I just had to write in python the tests.

Also the TinyTapeout template provides some GitHub Actions that compile the gds and provide 2D preview; 3D viewer and the Explorer (that I used a lot to test ASILUC).
